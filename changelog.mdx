## How to write release notes

<Steps>
  <Step title="Choose the release" icon="calendar">
    Start with a date and semantic version, such as `2026-10-18` and `v1.8.0`.
  </Step>
  <Step title="Group changes by type" icon="layout-list">
    Use sections like New Features, Improvements, Bug Fixes, Security Improvements, and Breaking Changes.
  </Step>
  <Step title="Keep entries specific" icon="file-text">
    Describe what changed, why it matters, and what users should do next.
  </Step>
  <Step title="Publish and link" icon="link">
    Add an anchor link for each major release so readers can jump to the right update quickly.
  </Step>
</Steps>

## Release workflow examples

<Tabs>
  <Tab title="Feature release" icon="rocket">

    Use this format when you ship new product behavior or workflow enhancements.

    ````markdown
    ## v1.9.0

    ### New Features

    - Added workspace-level activity summaries.
    - Introduced a new audit trail view for recent actions.

    ### Improvements

    - Reduced time to open large release histories.
    - Simplified changelog navigation for returning readers.
    ````

  </Tab>
  <Tab title="Security release" icon="shield">

    Use this format when you need to document access control or policy updates.

    ````markdown
    ## v1.9.1

    ### Security Improvements

    - Tightened session handling for authenticated users.
    - Added clearer guidance for token rotation and expiration.

    ### Bug Fixes

    - Fixed an edge case that could show stale permission labels.
    ````

  </Tab>
  <Tab title="Breaking release" icon="alert-triangle">

    Use this format when a change affects existing behavior or integrations.

    ````markdown
    ## v2.0.0

    ### Breaking Changes

    - Renamed deprecated settings to match the new configuration model.
    - Updated migration guidance for existing environments.

    ### Migration Notes

    - Review your current settings before upgrading.
    - Verify integrations after deployment.
    ````

  </Tab>
</Tabs>

## Fields to include in every entry

| Field | What to include |
|------|----------------|
| Version | A semantic version such as `v1.8.0` |
| Date | The release date in `YYYY-MM-DD` format |
| Summary | A short sentence describing the release |
| Tags | One or more categories such as feature, bugfix, security, or breaking |

## Common writing tips

- Write in active voice and explain what changed for your users.
- Keep each bullet focused on a single outcome.
- Avoid vague phrases like “miscellaneous updates” unless you add details elsewhere.
- If a release changes behavior, call it out explicitly so readers know whether they need to act.

<Callout kind="tip">

A strong changelog is short, specific, and easy to scan. Readers should understand the impact of a release in under a minute.

</Callout>

## Advanced notes

<Expandable title="What counts as a breaking change?" default-open="false">

A breaking change alters an existing workflow, setting, endpoint, or expected output. If users must change their configuration or update their process, document it here.

</Expandable>

<Expandable title="How do you handle internal-only changes?" default-open="false">

You can mention internal improvements when they affect reliability, observability, or release behavior. If the change does not affect users, keep it out of the public changelog.

</Expandable>

<Expandable title="What should you do before publishing?" default-open="false">

Review dates, version numbers, and links. Then verify that each update includes clear headings and that any migration steps are easy to follow.

</Expandable>
